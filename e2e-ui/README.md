# synload real-input UI e2e suite

A rerunnable, self-contained end-to-end suite that drives the **deployed
site** through a real Chromium browser with **genuine input** — the browser's
own input pipeline, not synthetic DOM events:

| Input | Mechanism |
|---|---|
| typing | `page.type()` → CDP key events |
| clicks | `page.click()` → CDP mouse events |
| file upload | `set_input_files` → the real `<input type=file>` pipeline |
| dropdowns | `select_option` → real `change` events |
| touch swipe | CDP `Input.dispatchTouchEvent` (touchStart/touchMove/touchEnd) |
| mouse wheel | CDP `Input.dispatchMouseEvent` `type=mouseWheel` |

## Run

```bash
python3 e2e-ui/run.py                      # against https://video.synload.com
E2E_UI_BASE=https://staging.example python3 e2e-ui/run.py
```

Exit code 0 = all passed (skips allowed), 1 = failures.

Prereqs: `ffmpeg` on PATH, `pip install playwright && playwright install chromium`.

## What it covers

| Module | Flow |
|---|---|
| `test_01_upload` | /login (real typing) → /upload → real file input → title auto-fill from filename → real-typed description/tags → Upload → redirect to /watch → worker transcodes to ready → video actually plays (currentTime advancing) |
| `test_02_studio` | /studio → find row → Edit → real-typed title/description/tags → visibility dropdown → Save → "Video updated" → verify via API → second edit back to public |
| `test_03_playlists` | /playlists → New playlist (real typing) → Create → watch page Save menu → add (checkmark) → API videoCount=1 → playlist page → remove video (X) → videoCount=0 → Delete (confirm dialog) → 404 |
| `test_04_notifications` | viewer UI: real like click + real-typed comment on owner's video → owner UI: bell → badge 2, panel shows both → click one (marks read, navigates) → badge 1 → Mark all as read → badge gone → API unreadCount=0 |
| `test_05_shorts` | 3 vertical shorts via /upload (Short checkbox) → worker ready → **phone 375×812**: genuine touch swipe → scroll exactly one card, active 0→1, playing card flips → **desktop 1280×720**: genuine mouse wheel → same |
| `test_06_big_upload` | generate a **>100 MB** 1080p video (testsrc2 @ 10 Mbit/s) → /upload real file input → title auto-fill → Upload → **prove the S3 multipart path is taken** (network: multipart/init + ≥3× 50 MB part PUTs — a single PUT this size 413s at Cloudflare) → redirect to /watch → worker transcodes to ready → video actually plays |
| `test_07_thumbnail` | ready video (API) → /studio → click "Thumbnail" on the row → genuine file chooser picks a generated solid-color JPEG → **verify the live site serves the new image** (API thumbnailUrl bytes SHA-256 match the upload) and it differs from the auto frame → studio row img updates |

## Self-cleaning

Every run registers its own users (`e2e-ui-<role>-<runid>@test.local`) and
creates its own videos with **real ffmpeg-generated bytes** (solid color +
burned-in label + running timecode), so the worker genuinely transcodes them
to `ready` — the full pipeline, no SQL flips. `run.py` deletes every video
and playlist it created in a `finally` block. Users are unique per run (no
user-delete API) — same convention as the API suite in `e2e/`.

## Evidence

Screenshots land in `.peckboard/ui-e2e/<run_id>/` (before/after states for
the swipe/wheel test, key moments elsewhere).

## Notes

- The suite targets the deployed site by default, so it exercises the real
  Cloudflare edge, the real worker, and the real storage.
- Runtime is a few minutes: six real videos go through the worker, including
  the >100 MB big upload (test_06) which adds the longest single upload.
- Shorts assertions are relative (scroll moved exactly one card, active index
  +1, playing card flipped), so they hold even if the feed contains other
  ready shorts.
